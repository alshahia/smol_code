## 1. Question

After M13 (audit integrity + redact expansion + audit reader CLI) shipped
2026-08-23, three candidate M14 plans were drafted and presented to the user:

- **Option A** — Audit log operational hardening (CLI + SPA + rotation)
- **Option B** — iptables enforcement for elevated network allowlist
- **Option C** — `_cli_subcommands.py` extraction + small UX polish

User chose to plan for all three as a multi-milestone sequence rather than
pick one. This doc captures the ordering, scope, and validation gates for each.

---

## 2. Sequencing rationale

The three options ship in **M14 → M15 → M16** order. The order is deliberate:

1. **M14 = Option A (audit log operational hardening)** — flows directly from
   M13. The audit primitives (`verify_chain`, `audit ls/grep/verify`) need
   to be exposed via the SPA + hardened by a real rotation path. This is the
   highest-value-per-LOC of the three; it also closes an existing operator-UX
   gap (the `/api/audit` stub).
2. **M15 = Option C (CLI extraction + small UX polish)** — `cli.py` has
   grown to 1078 lines after M13 added `_audit_main`. Mechanical refactor +
   two deferred polish items. Landed BEFORE M16 because adding a 4th tier
   (`M14 + others`) of CLI code first would just make M15's extraction
   larger.
3. **M16 = Option B (iptables enforcement)** — biggest lift, touches Docker
   privilege (`CAP_NET_ADMIN`). Deserves its own milestone where the
   Docker test harness + image setup get the focus they need. Punted to
   last because it has the highest risk and the longest feedback loop.

Each milestone stays self-contained (~1.5 person-days, ~25 new tests,
~300 LOC) — same cadence as M12.5 / M13.

## 5. M16 — iptables enforcement for elevated tier

### 5.1 Goal
Close v1.1 followup #1. When an `elevated` container starts with a
non-empty `network_allowlist`, install `iptables` rules inside the
container that **drop all egress except to the allow-listed hosts** and
log dropped packets to a container-local file.

### 5.2 Sub-milestones

| | Scope | LOC (est.) | Tests (est.) |
|---|---|---|---|
| **M16.1** | New Docker image `docker/elevated-iptables.Dockerfile` (extends the M4 elevated image) with `iptables` + an init script (`/usr/local/bin/elevated-iptables-init.sh`) that reads `SMOLCODE_NETWORK_ALLOWLIST` env (comma-separated CIDR/host list) and applies the OUTPUT chain rules | ~80 (Dockerfile + shell) | 0 (built but not unit-tested) |
| **M16.2** | Update the `elevated` Docker executor in `smolcode/src/smolcode/agents/elevated.py` to set `cap_add=["NET_ADMIN"]` + mount the init script + pass `SMOLCODE_NETWORK_ALLOWLIST` env (built from `tier.network_allowlist`) | ~50 | 0 |
| **M16.3** | Contract tests: mock `docker run` invocation, assert the right `--cap-add NET_ADMIN`, the right env, and the right image name are passed | ~120 | 8 |
| **M16.4** | Live integration test (skipped if Docker unavailable): launch the container with a known allowlist (`api.github.com`), confirm egress allowed via curl, confirm `example.com` egress blocked via curl returning timeout | ~60 | 2 (1 contract + 1 live) |
| **M16.5** | Audit log integration: emit one `{"event":"iptables_install","allowlist":[...],"rules_applied":N}` line when the init script runs | ~30 | 1 |
| **M16.6** | Decision doc 0020 + roadmap + README + security.md forward note backfill | docs | 0 |
| | **Total** | **~340 LOC** + Dockerfile + 1 shell script | **11 new tests** |

### 5.3 Exit criteria
- `pytest src/smolcode/tests/` → **expected ~844 passed** (833 + 11)
- Docker build: `docker build -f docker/elevated-iptables.Dockerfile -t smolcode-elevated:test .` → exit 0
- Live test: `smolcode --tier elevated --network-allowlist api.github.com "curl example.com"` → curl times out + audit log has `iptables_drop` entries
- `docs/security.md` §7.2 (elevated network policy) updated with the iptables mechanism
- Risk note: `CAP_NET_ADMIN` is the only new capability; documented in security.md §11 "what we do not defend against"

### 5.4 Files affected
- `smolcode/docker/elevated-iptables.Dockerfile` — NEW
- `smolcode/docker/elevated-iptables-init.sh` — NEW
- `smolcode/src/smolcode/agents/elevated.py` — pass `cap_add` + env
- `smolcode/src/smolcode/audit.py` — add `iptables_install` + `iptables_drop` event helpers
- `docs/security.md` §7.2 — update with iptables mechanism
- `docs/roadmap.md` — M16 row
- `docs/decisions/0020-m16-iptables-enforcement.md` — NEW

### 5.5 Risk register
- **R-M16-A**: `CAP_NET_ADMIN` is broad; could let an attacker who escapes the Python sandbox also modify iptables rules. Mitigation: install the init script as PID 1 via `docker run --init`, run all subsequent processes as non-root inside the container, and log every iptables rule modification to a read-only audit sink.
- **R-M16-B**: iptables rules are lost when the container stops; no persistent state. Acceptable (matches the existing short-lived agent model).
- **R-M16-C**: Host kernel must support `iptables` (not `nftables` only). Document the requirement in the Dockerfile's base image (pin to Ubuntu 22.04 LTS).
