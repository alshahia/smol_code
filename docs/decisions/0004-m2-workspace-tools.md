# M2 — Workspace tools (fs / shell / git) with class-attribute binding

**Date:** 2026-08-19
**Trigger:** Implementation of M2 (workspace tools with `PathPolicy` + command allowlist)
**Sources:** smolagents 1.27.0.dev0 `tools.py`, `tool_validation.py`, `utils.py`,
            `remote_executors.py`; existing `docs/architecture.md` §5.3, `docs/security.md` §5-6.
**Status:** active

## Question

How do smolagents Tool subclasses carry per-instance state (workspace
path, command allowlist, git cwd) across the Docker executor's
"serialize class source → exec on remote → instantiate with no args"
round-trip?

The naive approach — pass state through `__init__` — does NOT work,
because the remote side re-instantiates the class with `Cls()` (no
arguments). The smolagents docs say explicitly:

> "Args chosen at init are not traceable, so we cannot rebuild the
> source code for them, thus any important arg should be defined as a
> class attribute."
>
> — `smolagents/tool_validation.py:validate_tool_attributes`

## Findings

We tried (and discarded) four approaches:

1. **`@tool` closure with workspace passed in.** `instance_to_source`
   captures the closure's free variables into the serialized source,
   but `MethodChecker.visit_Name` then flags every name that is not a
   builtin / arg / import / class attr as **undefined**. Closures
   fail the validator before serialization even starts.

2. **`Tool` subclass with `__init__(self, workspace="")`.** The
   `__init__` source is captured, but the remote side calls
   `Cls()` with no args, so `self.workspace = ""` on the remote.
   Confirmed empirically: a diagnostic print of `self.workspace`
   inside `forward()` showed `""` (empty string), even though the
   host-side instance had the correct path.

3. **`Tool` subclass with workspace as a class attribute + same
   `__init__` shape.** Same bug — `__init__` overwrites the class
   attribute with `""`.

4. **Tool subclasses with `__init__(self)` only + per-build subclass
   with workspace baked in as a class attribute.** **This works**
   (probe-confirmed), but has two subtle constraints:

   - **`validate_tool_attributes` rejects "complex" class attrs.**
     The validator walks the class source AST and rejects any class
     attribute whose value contains an `ast.Load` node (because
     `ast.walk` on a list literal yields `Load` contexts). The
     concrete consequence: **list and tuple class attributes fail
     validation** even when every element is a literal Constant. Empty
     lists fail too.
   - **`get_source(cls)` requires `inspect.getsource` to succeed**
     for dynamically-created classes. By default it falls back to
     `getattr(obj, "__source__", None)`, so setting `cls.__source__`
     on the new class bypasses `inspect.getsource` and lets
     `validate_tool_attributes` work.

## Decision

We adopt approach 4 with two small additions:

- **Encode collections as pipe-separated strings** ("`python|git|pytest`").
  Forward() splits on demand. This avoids the `ast.Load`-in-list-literal
  trap. Documented in `tools/_bind.py`.
- **Set `cls.__source__`** on the per-build subclass so
  `validate_tool_attributes` and `instance_to_source` can both find the
  source. Implemented in `tools/_bind.py:bind_attrs`.

The per-build class is generated by `bind_attrs(base_cls, attrs)`. All
three tool factories (`build_fs_tools`, `build_shell_tools`,
`build_git_tools`) go through it.

The `__init__` of each tool class is `def __init__(self): super().__init__()`
with **no** state-setting. State lives in the class attributes baked
in by `bind_attrs`.

Policy logic (path traversal check, basename allowlist, Windows `.exe`
strip) is **inlined** in each `forward()`. A copy of the same logic
exists as a module-level helper for host-side tests, but the helper is
not referenced from `forward()` because `MethodChecker` would flag it
as undefined when the serialized class is re-validated.

`PolicyViolation` is **not** raised by the tool source. The tool raises
the built-in `PermissionError` instead, because the tool source runs on
the remote and cannot import from `smolcode.tools.policy` (NameError on
import). `PolicyViolation` is retained for host-side use in `PathPolicy`
and `CommandPolicy`.

  verifies the docker serialisation round-trip preserves state.

## Side-fix: Windows 8.3 short paths

`tempfile.TemporaryDirectory()` returns paths like
`C:\Users\AHMADM~1\AppData\Local\Temp\tmpXXXX` (8.3 short form).
`os.path.realpath` resolves them to the long form
`C:\Users\Ahmad Mahmoud\AppData\Local\Temp\tmpXXXX`. The previous
tool code normalized only the target path via `realpath`, leaving the
workspace as the 8.3 form, so `commonpath` returned `c:\users` (a
real mismatch) and even in-workspace writes were rejected as
"outside workspace".

Fix: also run `realpath` on the workspace string before `normcase`.
Applied at lines 48/93/135 of `fs.py` (and the same pattern is
applied to `PathPolicy._workspace_norm` via `Path(...).resolve()` on
the host side, which already worked).

This is Windows-specific. POSIX is unaffected.

## Known limitations (carried into later milestones)

- The per-build subclass approach is one-shot per `build_*_tools()`
  call. Concurrent builds for different workspaces are safe (different
  subclasses), but the helper does not cache.
- The `PathPolicy` on the host side uses `Path(...).resolve()` which
  on Linux behaves differently than on Windows. Both sides agree for
  relative paths inside `<repo>/workspace/`; absolute paths with
  symlinks are not yet covered by tests.
- Tools are still host-side in the docker case (the docker executor
  is only used for *code* execution by `CodeAgent`; the tools
  themselves run on the agent host). This is by design (see
  `docs/architecture.md` §5.3) but worth restating.
